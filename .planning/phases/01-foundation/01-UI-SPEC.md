# Phase 1 — UI Design Contract (Trunk Phase)

> Visual and interaction contract for the foundation phase of Shifter. Generated by `gsd-ui-researcher`, verified by `gsd-ui-checker`.
>
> **This is the trunk phase.** Every decision below propagates to Phases 2–7. Future phases inherit these tokens, conventions, and copywriting style — only domain-specific extensions are added per phase. Any later deviation from this contract requires an explicit revision documented at the top of that phase's UI-SPEC.

---

The Phase 1 contract must cover every interaction surface that ships in this phase. Listed for traceability against `gsd-ui-checker` and `gsd-ui-auditor`:

| Surface | Source REQ | Notes |
|---------|-----------|-------|
| Login screen | AUTH-01, AUTH-04 | Centered card on neutral surface, brand logo, single form |

## Spacing Scale

Tailwind 4 native scale (4px base — `space-{n}` where each unit = 4px). Declared values used in Phase 1 (multiples of 4 only):

| Token | Tailwind class | Value | Usage |
|-------|---------------|-------|-------|
| xs | `space-1` / `gap-1` | 4px | Icon-to-text gap, badge inner padding |
| sm | `space-2` / `gap-2` | 8px | Form-row inner gap, button inner gap |
| md | `space-4` / `gap-4` | 16px | Default form-field vertical rhythm, card body padding (top/bottom) |
| lg | `space-6` / `gap-6` | 24px | Card padding (left/right), section-internal padding, dialog body padding |
| xl | `space-8` / `gap-8` | 32px | Inter-section gap inside a settings page or wizard step |
| 2xl | `space-12` / `gap-12` | 48px | Major-section breaks (e.g., between "Account" and "ChirpStack" settings sections) |
| 3xl | `space-16` / `gap-16` | 64px | Login-page top padding on desktop; rarely used elsewhere |

**Density:** **Compact**. Operator console serves NOC-style users on large monitors who scan many rows. Defaults:
- Form field vertical rhythm: 16px (not 24px).
- Table row height (Phases 3+): 36px (not 44px).
- Button height default: 36px (`h-9`); large CTA: 40px (`h-10`); small/destructive: 32px (`h-8`).
- Dialog body padding: 24px (consistent with shadcn `new-york` defaults).

**Touch-target exception:** On viewports `<md` (mobile, <768px), interactive elements that are *primary actions* (Submit / Cancel in dialogs, nav items, the topbar account menu) raise to 44px minimum height to meet WCAG 2.1 AA touch-target guidance. Density stays compact for *content* (table rows, list items remain at 36px).

**No magic numbers.** Every margin, padding, gap, width, and height in implemented code MUST resolve to a Tailwind class from the scale above. Inline `style={{...}}` with raw px is forbidden except for: (a) Leaflet/react-leaflet container sizing (Phase 5), (b) floor-plan absolute-positioning (Phase 5).

### 60/30/10 enforcement

- **60% dominant** — `--background` on the main content area, all page bodies, all wizard step bodies. NEVER tinted blue.
- **30% surface** — `--card` on the left sidebar, all `<Card>` components, dialog bodies, settings section panels.
- **10% accent** — `--primary` is RESERVED for the elements listed below. Anywhere else uses `--secondary` or `--foreground`/`--muted-foreground`.

### Accent reserved for (exhaustive list — never broaden without amending this contract)

1. The `<Button variant="default">` (primary CTA in dialogs and forms — exactly one per surface).
2. The active sidebar nav item background.
3. The focused form ring (`--ring`).
4. Selected/checked state on `<Checkbox>`, `<Switch>` (later phases).
5. The brand logo bug in the topbar (light mode).
6. Inline links inside body copy (e.g., "See our setup guide" in the wizard) — text uses `--primary`, hover underline only.
7. Wizard active-step indicator dot.

**Forbidden accent uses:** decorative blocks, gradient backgrounds, status badges (those use `--success`/`--warning`/`--destructive`/`--info`), table header rows, card hover states (use `--secondary` for hover), table row stripes (don't stripe — use `--border` separators).

### Semantic palette is NOT an afterthought

Phase 1 ships four semantic colors (`success`, `warning`, `destructive`, `info`) as first-class tokens because Phase 4+ alert center, Phase 1 Test Connection, and Phase 6 backup-status surfaces all depend on them. Defining them now means they propagate cleanly into shadcn's CSS variable system without a later refactor.

### Brand colors are NEVER hex literals

The executor MUST reference `bg-primary`, `text-success`, `border-destructive` etc. — NEVER `bg-blue-700` or `bg-[#1E40AF]`. The CSS variable layer is the single source of truth so dark-mode swap is automatic and any future preset-tweak is one file change.

## Layout & App Shell

### Login screen (no shell)

- **Container:** Centered card on neutral background, max-width 400px, vertical-centered with 64px top padding on desktop, 32px on mobile.
- **Card padding:** 32px (`p-8`).
- **Order top→bottom:** Brand logo (40px tall) + product name "Shifter" `text-2xl` → "Sign in to Shifter" h2 (`text-lg`) → description (`text-sm text-muted-foreground`) → form (email, password, submit) → footer text "Forgot password? Contact your administrator." (`text-sm text-muted-foreground`).
- **Submit button:** full-width, `variant="default"`, label "Sign in" (NOT "Login" or "Log in").
- **Logo placement on login:** centered above heading. The install identity logo (configured in wizard) does NOT appear on the login screen — the login screen only shows the **Shifter product logo**, because the install identity is per-customer brand context that is set after login. Phase 1 ships a default Shifter wordmark; the install can override the post-login topbar logo only.

### Force-change-password screen (no shell)

- Same container shape as login (centered card, max-width 400px).
- Heading: "Change your password" (`text-2xl font-semibold`).
- Body: "Your administrator set a temporary password. Choose a new one to continue." (`text-sm text-muted-foreground`).
- Three fields: Current password, New password, Confirm new password.
- Password strength meter inline below "New password" using `<Progress>` (4-segment: weak/ok/good/strong). Color: `--destructive` → `--warning` → `--info` → `--success`.
- Submit label: "Set password" (NOT "Save" — verbs always pair with the noun being changed).

### Install wizard (full-screen stepped dialog)

- **NOT a `<Dialog>` overlay.** First-run wizard is a full-screen route at `/install` that renders a centered card (max-width 720px on desktop, full-bleed with 16px page padding on mobile).
- **Step indicator:** horizontal at top of card, 5 numbered steps with checkmarks for completed. Steps:
  1. **Admin** — create initial admin user (email, name, password)
  2. **ChirpStack** — mode (radio: bundled / external) + gRPC URL + API token + MQTT URL fields. v3 detection at submit-time → blocks step with destructive banner.
  3. **Region** — `Select` with regulator-aware groups. Default group "Asia" expanded with "Thailand (AS923-2)" pre-selected (per STATE.md Phase 1 acceptance check). Other groups: Europe (EU868), Americas (US915, AU915), etc.
  4. **Identity** — display name, logo upload (PNG/JPG, max 256KB, square ≥ 64×64), address, timezone (`Select` with `<install-tz>` system default), units (radio group: metric / imperial — default metric since LoRaWAN deployments cluster outside US).
  5. **Review** — summary of all 4 prior steps with "Edit" links + "Finish setup" CTA.
- **Navigation:** "Back" (ghost, left) + "Next" (default/primary, right). Final step "Next" becomes "Finish setup".
- **Cancel:** No cancel — wizard runs once. If browser closes mid-wizard, the partial state is dropped; next page load resumes at step 1 with empty fields. (Phase 1 simplification — Phase 6 may add resume-from-step-N if real installs report friction.)

## Dialog Conventions (CRITICAL — propagates to every later phase)

Per UX-01, **all CRUD lives in dialogs**. Phase 1 establishes the canonical pattern.

### Sizes

| Size | Tailwind class | Width | Use |
|------|---------------|-------|-----|
| `sm` | `sm:max-w-md` | 448px | Single-action confirmations, "Toggle theme", small forms (≤ 3 fields) |
| `md` (default) | `sm:max-w-lg` | 512px | Standard CRUD forms (Phase 1: Change password, Edit ChirpStack connection) |
| `lg` | `sm:max-w-2xl` | 672px | Stepped flows (Phase 2: Add device, Meter swap), forms with 5+ fields |
| `xl` | `sm:max-w-4xl` | 896px | Reserved for review-style dialogs in later phases (Phase 3 bulk import preview) |

Phase 1 uses **md** for "Edit ChirpStack connection" and "Change password"; **sm** for any single-field confirmation.

### Position

- Desktop: centered, vertically anchored 10% from top so the dialog doesn't reflow on virtual-keyboard open in nested mobile views.
- Mobile (`<md`): full-screen sheet from bottom, dragging the top handle dismisses (uses shadcn `<Sheet side="bottom">` instead of `<Dialog>`). The dialog/sheet swap is automatic via a `<ResponsiveDialog>` wrapper component the executor builds in Phase 1 — **mandatory** because every later phase uses CRUD dialogs and they all must respect this responsive shape without re-implementing it.

### Anatomy

```
┌──────────────────────────────────────┐
│  Header                               │
│  ┌─────────────────────────────────┐  │
│  │ <DialogTitle>  text-lg semibold │  │
│  │ <DialogDescription> text-sm muted│  │
│  └─────────────────────────────────┘  │
│  ───────── (separator if footer is destructive) │
│  Body                                 │
│  ┌─────────────────────────────────┐  │
│  │ Form fields (gap-4 vertical)    │  │
│  │ Helper text below each field    │  │
│  │ Validation errors inline-below  │  │
│  └─────────────────────────────────┘  │
│  Footer                               │
│  ┌─────────────────────────────────┐  │
│  │  [Cancel ghost-left]   [Confirm primary-right] │
│  └─────────────────────────────────┘  │
└──────────────────────────────────────┘
Padding:  header  px-6 py-5
          body    px-6 py-4 (gap-4 between fields)
          footer  px-6 py-4 with border-t
```

- **Header always present.** Title is a strong verb + noun ("Change password", NOT "Password" or "Edit").
- **Description is optional** but always uses `text-sm text-muted-foreground`. Used when the title alone doesn't tell the operator what changes.
- **Footer always has Cancel on the left, primary action on the right.** This direction is FIXED — every dialog in every phase. (Operator-console muscle memory matters more than platform conventions.)

### Behavior

- **Backdrop click:** dismisses non-destructive dialogs only. Destructive dialogs (`<AlertDialog>`) require the explicit Cancel click.
- **Escape:** dismisses any dialog (including destructive — Escape is "I changed my mind", not "I confirmed").
- **Submit on Enter:** when focus is in the last form field. NEVER submits when focus is in a textarea (newline takes precedence).
- **Loading state:** primary button shows `<Loader2>` icon spinning + label changes to gerund form ("Saving…", "Testing connection…", "Setting password…"). Cancel remains clickable.
- **Error state:** if the submit fails, the dialog stays open, the primary button returns to default state, and an inline `<Alert variant="destructive">` appears at the top of the body with the error. Toast is NOT used for in-dialog errors (the operator is already focused on the dialog).
- **Success:** dialog closes, then a `sonner` toast fires with `variant="success"` and a present-tense confirmation ("Password changed", NOT "Password was changed").

### Destructive confirmation pattern

For any destructive action (Phase 1: zero in scope; future phases: delete user, delete device, revoke sessions), use shadcn `<AlertDialog>`:

- Title: action verb in imperative ("Delete this user?").
- Description: states the consequence including any cascade ("All sessions will be revoked. The audit history is preserved.").
- Confirm button: `variant="destructive"`, label is the verb-noun ("Delete user", NOT "Confirm" or "Yes").
- Type-to-confirm: required ONLY when the destructive action is irreversible AND affects shared state (Phase 6: drop database, factory reset). Phase 1 has no such action.

### Stepped dialog pattern (install wizard)

The install wizard at `/install` is the canonical stepped flow. Pattern reused in Phase 2 (Add device dialog), Phase 5 (Floor-plan upload + placement), Phase 7 (Codec test-runner).

- Step indicator at top: `<Progress>` bar OR a numbered horizontal step list with checks. Phase 1 uses the numbered list. Steps render as: pill-shaped circles 28px, current step `--primary`, completed steps `--success` with check icon, future steps `--muted-foreground`.
- Footer has 3 zones: `[Back ghost-left]` `[step indicator center text "Step 2 of 5"]` `[Next primary-right]`.
- The "Back" button is disabled on step 1; "Next" becomes "Finish" on the final step.
- Each step is a fresh form scope — validation runs on Next, blocks the step transition if invalid.

```
<FormField>
  <FormLabel>Field label</FormLabel>           text-sm font-semibold
  <FormControl>
    <Input ... />                              h-9 (36px), text-sm
  </FormControl>
  <FormDescription>Helper text.</FormDescription>  text-sm text-muted-foreground
  <FormMessage />                              text-sm text-destructive (only when error present)
</FormField>
```

- **Label position:** above the input. Labels are NEVER inline-left, NEVER floating, NEVER placeholder-as-label. Reason: form fields in Phase 1 wizard go up to 5 stacked; placeholder-as-label patterns are universally less accessible.
- **Helper text position:** below the input, before the error message. Not in a tooltip.
- **Required indicator:** trailing red asterisk `*` styled `text-destructive` next to the label. Tooltip on hover: "Required". The form-level "required fields are marked *" footnote is shown once at the top of any form with ≥1 required field.
- **Error display:** inline below the field, `text-sm text-destructive`. Error text is a complete sentence with a fix path ("Enter at least 12 characters." NOT "Min 12.").
- **Async validation:** for fields validated server-side (e.g., wizard step 2 ChirpStack URL → "Test reachability" inline), show a `<Loader2>` spinning to the right of the input while the request is in flight, then a green check or red X icon once resolved. Color: `--success` / `--destructive`.
- **Field width:** inputs default to full-width of the form container (`w-full`). Numeric / short fields (timezone, port) may be narrower (`max-w-xs`).
- **Disabled state:** `opacity-60 cursor-not-allowed`. Disabled fields explain why via a tooltip on hover ("Disabled because ChirpStack mode is bundled.").

### Validation timing

- **On blur** for individual fields (typed-in errors clear when corrected and re-validated on blur).
- **On submit** for the whole form (clicking primary button validates all fields, focuses the first invalid one).
- **NOT on every keystroke** — too noisy for a dense form like the wizard.

## State Conventions

### Loading

| Surface | Pattern |
|---------|---------|
| Whole-page initial load | Centered `<Loader2>` 32px on `--background`, no skeleton on first paint (the binary serves the shell HTML synchronously). |
| Within-page data load | `<Skeleton>` placeholders matching the final shape for tables/lists. Phase 1 has no list surfaces; Phase 3+ uses skeletons. |
| Inline action in progress (e.g., Test Connection) | Inline `<Loader2>` + status text "Testing gRPC…" / "Testing MQTT…" updating per channel. |
| Dialog submit | Primary button `<Loader2>` + gerund label, button stays width-stable so layout doesn't shift. |

### Empty

Phase 1 has one empty surface: the avatar dropdown's notifications area (Phase 6 surface — Phase 1 hides the bell entirely, no empty state needed). The settings sections always show data (account exists, ChirpStack connection exists post-wizard).

The Phase 1 contract for empty states (referenced by Phase 2+):

- **Container:** Centered in the parent, vertical padding 48px.
- **Icon:** 40px lucide icon, `text-muted-foreground`.
- **Heading:** `text-lg font-semibold`. Describes what's missing in plain words ("No devices yet", NOT "Empty").
- **Body:** `text-sm text-muted-foreground`. One sentence explaining what to do next.
- **CTA:** primary button with the action that creates the missing thing ("Add device", "Create site"). Optional but encouraged.

### Error

| Surface | Pattern |
|---------|---------|
| Whole-page failure (network down, 500 from `/health`) | Centered `<Alert variant="destructive">` with heading "Something went wrong", body explaining the failure category, "Retry" button. NOT a blank screen, NEVER a stack trace. |
| In-dialog submit error | Inline `<Alert variant="destructive">` at top of dialog body. Title is the failure category ("Couldn't reach ChirpStack"). Body has the actionable next step ("Verify the gRPC URL and try again."). |
| Per-field validation error | `<FormMessage>` text in `text-destructive`, inline below field. |
| Live channel offline (Phase 4 SSE drop) | Top-of-app banner using `<Alert variant="warning">`. Phase 1 N/A. |

### "Test Connection" result UI (Phase 1 specific)

Result panel renders below the "Test connection" button after the operator clicks it:

```
┌─────────────────────────────────────────────────────────┐
│  ● gRPC      Reachable     47 ms                        │   ← --success
│  ● MQTT      Reachable     12 ms                        │   ← --success
└─────────────────────────────────────────────────────────┘

or (failure)

┌─────────────────────────────────────────────────────────┐
│  ● gRPC      Unreachable   connect: connection refused  │   ← --destructive
│  ○ MQTT      Skipped       (gRPC failed first)          │   ← --muted-foreground
│                                                         │
│  Verify the gRPC URL and that ChirpStack is running.    │
└─────────────────────────────────────────────────────────┘
```

- Channel rows use the canonical status-row component (status dot + label + monospace detail).
- On full failure, the bottom of the panel shows a single "next step" sentence, not a list of bullet remediation steps. Operator-console UX favors one immediate action.

## Copywriting Contract

Phase 1 copy is the trunk — voice and tone propagate to every later phase.

- **Direct.** Operator console, not a consumer product.

- **Plain English for failures.** "We couldn't reach ChirpStack." NOT "Connection failed: ECONNREFUSED at tcp:127.0.0.1:8080."
- **Codes are subordinate.** Show the human sentence first; show the technical detail in monospace below or in a `<details>` collapsible.

## Accessibility

- All form inputs have associated `<Label>` (shadcn `<FormLabel>` does this).
- All icon-only buttons have `aria-label` matching the action verb.
- Focus ring uses `--ring` (semi-transparent primary) — visible on all interactive elements, never `outline: none` without replacement.
- Color contrast: every text/background pairing in the palette declared above passes WCAG AA (verified at preset definition; checker re-verifies).
- Status communication is **never color-only** — every status row has an icon AND a text label (e.g., "Reachable" + green check, NOT just a green dot).
- Keyboard support: dialogs trap focus, Escape dismisses, Enter submits when focused on the last field.
- Reduced motion: `prefers-reduced-motion` disables the `Loader2` spin (it becomes a static icon) and disables `<Sheet>` slide animation.
